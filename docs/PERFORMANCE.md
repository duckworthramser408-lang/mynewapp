> Android 0.5 现在会在 LUT 之前加入本地美颜，实际改变像素时还顺序生成同 LUT 基线。下面的 0.4 基准只代表 LUT 旧路径优化，不能当作含美颜的整次拍摄时间。0.5 分段记录与范围见 [验收状态](ACCEPTANCE.md) 和 [beauty-host-0.5.json](performance/beauty-host-0.5.json)。

# 拍照后冲洗慢的原因与 0.4 优化

旧版实际执行了实验相机的完整流水线：读取整张原片、运行基础调色引擎、应用 LUT、编码完整 PNG、生成两张缩略图、逐像素抽样统计、写参数和分析 JSON、计算多文件哈希。每张照片还复制并校验一份约 1 MB 的 LUT。界面用不可取消的对话框等待整套流程结束，最后重新绑定相机，所以处理耗时全部变成了不能继续拍照的等待。

## 已实施的变化

- 新照片只进行 sRGB 解码／画幅裁切、直接原地 LUT 插值、JPEG 95 编码和一张胶片缩略图。不再经过中性基础调色，也不创建实验参数、统计、历史或导出数据。
- LUT 按胶卷 ID 缓存，Android 在后台校验解析一次并复用；鸿蒙源码在 TaskPool 解析并缓存，避免在界面线程解析几万行文本。原始用户 LUT 资源不变。
- JPEG 写入后立即恢复快门，保留相机会话，不因一次冲洗完成而重新开相机。Android 使用串行 WorkManager 队列，预览缩略图用独立的 I/O 执行器，避免被冲洗任务堵住。
- 完整图像处理串行，Android 工作线程降低 CPU 优先级，减少连续拍摄时争用。内存不足或处理失败保留原片，预览可重试。
- 删除先原子移走照片目录，再清理文件，避免正在冲洗的任务把已删除照片重新写回相册。

JPEG 95 是有损输出，和旧版无损 PNG 的文件大小、压缩策略不同。原片仍保持相机 JPEG 文件，保存原片直接复制；没有为测速而缩小输出分辨率。

## 云端基准

命令：`source tools/env.sh && python3 -m tools.benchmark_film`。

同一张 4000×3000 的程序生成纹理 JPEG，同一款用户提供的“理光GR”33³ LUT，旧／新各 3 次，取中位数。主机为 x86_64 Linux，C++ `-O2`，编解码使用 Pillow/libjpeg/libpng。LUT 预先解析，冷解析单独记录约 60 ms。

| 阶段 | 旧路径 | 新路径 |
|---|---:|---:|
| 解码与缓冲 | 178.65 ms | 171.45 ms |
| 基础调色 | 399.89 ms | 跳过 |
| LUT 插值 | 270.14 ms | 276.73 ms |
| 编码与 RGB 输出转换 | 2744.13 ms（PNG） | 131.45 ms（JPEG 95） |
| 总耗时中位数 | 3581.79 ms | 572.08 ms |
| 单张文件大小 | 34.79 MB | 9.89 MB |

这一主机工作负载约加速 **6.26 倍**。旧路径基准还没有计入统计、哈希、逐张复制 LUT、缩略图和界面重建，不能把它称为旧版端到端耗时。编码前完整像素 SHA-256 一致，验证直接 LUT 路径与“中性基础调色 + LUT”相同；JPEG 编码后的像素自然会因有损压缩出现差异。

**这些数字不是手机实测，也不是连续拍摄时的实时性保证。** 不同纹理、手机 SoC、摄像头 ISP、分辨率、存储和 JPEG 编码器都会改变结果。原始运行数据见 [基准记录](performance/film-host-0.4.json)，脚本输出在 `.build/film-benchmark.json`。

## 进一步加速的验证方向

Android `FilmDevelop` 日志记录解码、LUT、JPEG／缩略图三个阶段耗时，不记录用户的调色参数或图像分析数据。拿到真机后先根据这些时间定位瓶颈。如果 LUT 仍是主要开销，再评估 OpenGL ES 3D 纹理或 Vulkan 计算，验证各机型的颜色与像素误差；当前无需为了尚未测得的瓶颈引入 GPU 上下文和驱动兼容成本。鸿蒙异步桥目前仍有图像缓冲复制，可在 SDK 与设备可用后评估减少跨层复制。
